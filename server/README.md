# Прогностика 2027 — сервер

Розрахунок без ШІ: формули (`engine.js`) і точні ключі текстів (`forecast.js`). Без зовнішніх залежностей, Node.js 20+.

## Запуск

```bash
CONTENT_PATH=/шлях/до/content.json node server.js
```

| Змінна | За замовчуванням | Призначення |
|---|---|---|
| `PORT` | `8787` | порт |
| `HOST` | `127.0.0.1` | адреса; за проксі (nginx/Caddy) залишити `127.0.0.1` |
| `CONTENT_PATH` | `../private/content.json` | база текстів; **ніколи не класти в git чи публічну папку** |
| `ALLOWED_YEARS` | `2027` | доступні роки прогнозу |
| `PERIOD_MODE` | `birthday_after_15` | або `calendar` |
| `DEV_PLAN_PARAM` | вимкнено | `1` — тариф із `?plan=` для локального демо; сервер відмовиться стартувати з ним на не-локальній адресі |

## Тести

```bash
npm test
```

Формули на контрольних прикладах ТЗ, наявність усіх ключів для 2 000+ дат, доступ за тарифами, безпека HTTP (шляхи, криві запити, ліміти, заголовки).

## Перед бойовим запуском (обовʼязково)

1. **Оплата → доступ.** Реалізувати `getEntitlement()` у `server.js`: перевірка Telegram `initData` (HMAC з токеном бота) і оплачених замовлень за `telegram_user_id`. Доступ відкривати лише за підписаним webhook платіжної системи (сума, валюта, `order_id` мають збігатися; повторний webhook — ідемпотентно).
2. **HTTPS** через проксі (Caddy/nginx) + HSTS на проксі.
3. **Обмеження частоти запитів** на проксі (наприклад, 30 запитів/хв з IP до `/api/`).
4. `content.json` — права лише для користувача сервісу (`chmod 600`), резервна копія поза сервером.
5. Статичну версію (`docs/`, GitHub Pages) використовувати **лише для тестування**: у браузер передається вся зашифрована база, і будь-хто з посиланням-ключем може її отримати.
